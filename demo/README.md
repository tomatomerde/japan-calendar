# デモページ

ブラウザだけで動くデモの元ファイル。`.github/workflows/pages.yml` が
build → ブラウザ検証 → GitHub Pages へのデプロイまでを行う。
公開先は `https://tomatomerde.github.io/japan-calendar/`。

## 手元で動かす

```sh
./demo/build.sh          # demo/_site を組み立てる（レジストリから公開版を取得する）
npm run test:demo        # 組み立てた _site を実際の Chromium で検証する
npx serve demo/_site     # 目で見たいとき（http で配る必要がある。ESM は file: で動かない）
```

`demo/_site` は生成物なので commit しない（`.gitignore` 済み）。

## 決めたことと、覆すときにどこを触るか

| 決定 | 理由 | 覆すとき |
| --- | --- | --- |
| **npm 公開版を固定して読み込む**（このリポジトリのソースをビルドしない） | 訪問者が `npm install` して得るものと、ページで見えるものを一致させるため。作業中のツリーを載せると、まだ誰も入手できない挙動を宣伝することになる | `demo/pinned-version.txt` |
| **esbuild で1ファイルにまとめる** | 公開パッケージは `tsc` の出力（相対 import を持つ複数ファイル）で、そのままではブラウザが1ファイルずつ取りに行く。バンドルは gzip 12KB で、遅延ロードの必要もない | `build.sh` の esbuild 呼び出し |
| **ページが述べる数値をライブラリから読む** | 対応年・公式データの範囲・取得日・SHA-256・出典 URL を HTML に直書きすると、データ更新のたびに黙って古くなる。`OFFICIAL_META` と `MIN/MAX_SUPPORTED_YEAR` を読んで描画すれば、ずれようがない | `app.js` の `renderFacts` と `index.html` の `data-fact` |
| **外部リクエストをゼロにする**（Web フォント・CDN・解析タグを一切使わない） | 「入力はブラウザの外に出ない」と書く以上、フォント1つでも外から取ればその主張が嘘になる。解析タグを入れない判断も同じ | `demo/style.css`（フォント指定）と `demo/index.html` |
| **ページの言語は日本語** | 日本の祝日・営業日・和暦を必要とするのは日本語で業務を書いている人で、流入も日本語の記事から来る。README を英語基準にしている方針とは、読み手が違うので衝突しない | `demo/index.html`（英語版を足すなら別ファイルにして相互リンク） |
| **初期値を公式データの範囲外（2028年）にする** | 「データが覆っていない年でも答えられる」がこのライブラリの主張なので、覆っている年を初期表示にすると主張が見えない。同時に「暫定」バッジも初期表示で出る | `app.js` の `PRESET_HOLIDAYS[0]` |
| **`national` と `bank` の両方を常に並べる** | 差が出るのは年末年始をまたぐときだけで、プリセットが日付を入れるだけでは利用者がラジオを切り替える理由に気づけない | `app.js` の `renderBusiness` の「national と bank の差」 |
| **飛ばした非営業日の一覧は 60 件で打ち切る**（打ち切ったことは明記する） | `+30000` を入れられると 14,000 行が DOM に載って1.4秒固まった。黙って切ると、検算材料として出している一覧が「全部」に見えてしまう | `app.js` の `renderBusiness` の `LIMIT` |

## 「入力の受け口」パネルが本体の検査になっている

パネル4は、ありがちな日付の書き方を**その場で実行して**結果を並べる。
各ケースには `expect: "accept" | "refuse"` を持たせてあり、**実際の挙動が
それと食い違うとページに警告が出て、`scripts/verify-demo.mjs` が落ちる**。

狙いは広報ではなく検査のほう。祝日ライブラリが日付を1日読み違えても例外は出ず、
**違う日の答えが自信を持って返ってくるだけ**で、それが営業日計算に乗ると増幅する。
公開版が受け付ける入力の範囲が変わったとき、このリポジトリでそれに気づく仕掛けは
他に無い（本体のテストは本体のソースに対して走るので、公開済みの版は見ていない）。

## タイムゾーンの節を Chromium で3か所から検証している

`verify-demo.mjs` は Asia/Tokyo・America/Chicago・Pacific/Kiritimati の3つで
ページを開き、次の両方を検査する:

- **暦の日付（文字列・オブジェクト）の答えは3か所で同じ。** JST 固定が壊れたらここが割れる
- **`new Date(y, m, d)` は3か所で同じにならない。** UTC+14 ではローカル 0 時が、
  UTC−5 ではローカル正午が、それぞれ別の JST 日付に落ちる

2つ目を検査しているのは、デモが「ずれる例」を見せられなくなったときに気づくため。
**「日本より西ではずれる」のような要約は書いていない**——実測すると逆で、
ずれるのはローカル 0 時なら UTC+9 より東、ローカル正午なら西。
どちらか一方を断定すると、読者の半分にとって自分のブラウザが反証する文章になる。
ページはルールを述べず、**その場で実行した結果**を出す。

## リリースのたびに要る作業

新しいバージョンを publish したら **`demo/pinned-version.txt` を上げる**。
上げないとページは古い版の挙動を見せ続ける。忘れても静かに壊れるだけなので、
`build.sh` はレジストリの `latest` と食い違うときに warning を出し、
`pages.yml` の週次 `pin-freshness` ジョブが赤くする
（`docs/releasing.md` にも手順として書いてある）。

## なぜ検証をワークフローに入れてあるか

ページは訪問者に約束している——**何も打たなくても結果が見える**こと、
**読み込み後は何を入力してもリクエストが発生しない**こと、
**日付演算が日本時間に固定されている**こと。どれも本物のエンジンでしか
確かめられないので、`scripts/verify-demo.mjs` が Chromium で実際に操作して検証し、
デプロイはその後にしか進まない。約束を書いたページを、約束を確かめずに配らないため。
